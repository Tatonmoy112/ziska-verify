# Architecture — the layer rules

These cases check the layer rules of `final.md` §3, §4 and §11 on the imports of every hand-written file in `lib/`. They come from the production audit, step 2, finding P-1 ([docs/production-audit.md](../production-audit.md)).

TC-ARCH-019 … -021 and -023 … -025 run in `test/architecture/doc_references_test.dart`; TC-ARCH-026 … -028 run in `test/core/network/api_routes_test.dart`; TC-ARCH-029 … -031 in `test/core/network/api_client_test.dart`; TC-ARCH-032 … -034 in `test/core/network/api_data_test.dart`; TC-ARCH-035 … -037 in `test/architecture/state_equality_test.dart`; TC-ARCH-001 … -011, -015 … -018 and -022 run in `test/architecture/layer_rules_test.dart`, and TC-ARCH-012 … -014 (the verification use cases, P-3) in `test/features/verification/domain/verification_usecases_test.dart`, both in CI with the other tests. The checker is `test/architecture/layer_rules.dart`. It reads only text: no plugin and no network.

## The rules

| Rule | Never allowed |
|---|---|
| R1 | `core` imports a feature or `app` |
| R2 | `shared` imports a feature or `app` |
| R3 | a feature imports `app` |
| R4 | a feature imports another feature, except the app-wide profile entity and Cubit (§4) |
| R5 | `presentation` imports `data` |
| R6 | `domain` imports `data` or `presentation` |
| R7 | `data` imports `presentation` |
| R8 | `domain` reaches Flutter (`package:flutter`, `dart:ui`), directly or through any file it imports |
| R9 | `domain` reaches a package that is not pure Dart, directly or through any file it imports (allowed: `clock`, `collection`, `freezed_annotation`, `intl`, `json_annotation`, `meta`, `timezone`; and no `dart:io`, `dart:html`, `dart:ffi` …) |
| R10 | a plugin is imported outside `core`. A plugin is any package whose pubspec has `flutter: plugin:`, read from `.dart_tool/package_config.json`, so a new plugin is covered automatically |
| R11 | `get_it` is imported outside `app` |
| R12 | `dio` is imported outside `core`, a feature's `data` and `app` |
| R13 | a feature file is outside `data`, `domain` and `presentation` |
| R14 | `presentation` imports a repository interface: blocs reach data through use cases only (P-3) |
| R15 | a `presentation`, `data` or `shared` file reaches a plugin through the files it imports (a direct import is R10, the domain R9; `main` and `app` compose the app) (P-7) |
| R16 | a `core` file that declares an interface also imports a plugin: the interface and the plugin live in separate files (P-7) |
| R17 | `core` folders depend on each other in a circle; a subfolder counts as a folder of its own (P-8) |
| R18 | a feature names another feature's route (`RouteNames.…`): it opens only its own feature's routes and Home, anything else through a router callback; comments are not navigation (P-9) |
| R19 | a feature's `data/services/*_api_service.dart` is not an `abstract interface class …ApiService` with a `Dio…` class implementing it (P-14) |
| R20 | an `ApiRoute` is made outside `core/network/api_routes.dart`: every route of the API is in `ApiRoutes` (P-17) |
| R21 | a feature's `data/` imports one of its use cases: a use case calls a repository, never the reverse (P-29) |

**A known break** that has a planned fix is listed in `knownBreaks` in the test, with its finding. A fixed one must be taken off the list (TC-ARCH-002). The list is empty: its one entry, P-2 (Profile → History's `CheckTotalsCubit`), was fixed on 2026-11-24.
